# Issue #17: сохранение связей после переноса и изменения тегов

> Более поздняя [заключительная проверка](release-0.9.1-final-smoke.md) выявила и исправила
> сброс позиции при переносе играющего трека; она содержит актуальные APK и результаты.

Дата: 15 октября 2026. Ветка: `codex/adversarial-0.9.1`.
Код и релизные APK: чистый коммит `d7ae28000638c64c250ba131059723178e154193`.

В [issue #17](https://github.com/Nikita-sud/latentjam/issues/17) описано исчезновение
песен из плейлистов и статистики после обработки в Picard и переименования путей.
Причина подтверждается кодом: Android MediaStore может выдать файлу новый ID,
а плейлисты и история продолжают ссылаться на прежний. Это не доказывает удаления
самих записей истории. Предыдущий adversarial review этот сценарий не покрывал.

Реализовано консервативное сохранение связей для однозначного случая. Проверки
ниже не выявили регрессий. Общее распознавание по любому MBID/AcoustID и восстановление
уже потерянных до обновления связей не заявляются.

## Что изменилось

Android хранит соответствие собственного ID трека и текущей строки MediaStore
в отдельном атомарно записываемом реестре. После подтверждённого переноса ID
приложения остаётся прежним, а адрес аудио, ревизия, путь и теги берутся из новой строки.
Поэтому плейлистам, избранному, истории и скрытым трекам не нужна миграция
нескольких хранилищ. Экспорт плейлистов обращается к текущему пути. Очередь получает
новый URI только для перемещённых файлов; обычный рескан не заменяет её источники.

Автоматическое сопоставление требует всех условий:

- Метаданные исходного файла были прочитаны и сохранены до переноса.
- Исходная строка отсутствует в полном запросе аудио MediaStore, включая строки
  вне музыкального фильтра; хранилища доступны.
- Новый файл ещё не получил самостоятельную известную запись в реестре.
- Его MusicBrainz **release-track ID** совпадает ровно с одной исторической записью
  и встречается ровно один раз среди текущих музыкальных файлов. Известные ранее
  дубликаты тоже запрещают автоматическое объединение.
- Совпадают непустой том и расширение файла; обе длительности положительны
  и отличаются не более чем на секунду. Если у обоих файлов есть recording ID,
  они должны совпадать.
- Нет непрочитанных потенциальных дубликатов на этом томе.

Release-track ID относится к позиции на конкретном релизе. Один recording ID может
относиться к нескольким релизам, поэтому его недостаточно. Использованы
[официальные поля Picard](https://picard-docs.musicbrainz.org/en/latest/appendices/tag_mapping.html)
и [определение Recording в MusicBrainz](https://musicbrainz.org/doc/Recording).
Поддержаны MP3 ID3v2.3/v2.4, FLAC, Ogg Vorbis/Opus и M4A с iTunes freeform.
По названию, исполнителю, ISRC или AcoustID сопоставление не производится.

Чтение метаданных ограничено 8 МиБ на файл. Повреждённые, усечённые и слишком большие
теги не дают оснований для сопоставления; большие FLAC-картинки пропускаются без
загрузки тела. Первичное изучение тегов выполняется в фоне, повторные сканы
не перечитывают неизменившиеся файлы. Реестр сохраняется одной записью за проход.
Отмена или неудачная запись не публикует несохранённое соответствие. Повреждённый
реестр сохраняется для диагностики, а скан не объявляется полным.

Библиотеки без подходящих тегов сохраняют прежние ID и поведение. iOS не включает
этот механизм. По MBID не переносятся результаты аудиоанализа: новый URI/ревизия
по-прежнему требуют проверки кэша и при необходимости повторного анализа.

Во всех перечисленных тестах 0 ошибок и 0 пропусков. Количества прочитаны из
JUnit XML. Незатронутые history/smart host-задачи были актуальны по Gradle;
задачи затронутых модулей выполнялись. Полный прежний iOS-набор не выдаётся
за повторно выполненный: здесь заново запущены library и composeApp.

Новые 13 host-тестов реестра и 8 общих тестов парсеров проверяют повторный перенос
и перезапуск, дубликаты, разные релизы, неподходящий том/формат/длительность,
отсутствующую SD-карту, неполный запрос, ошибки чтения/записи, отмену, повторное
использование числового MediaStore ID, повреждение реестра и устаревший фоновый
результат. Проверка 500 неизменившихся треков подтверждает отсутствие повторных
чтений тегов и записей реестра; это не замер времени или энергопотребления.

Новый инструментальный тест создаёт настоящий MP3 и строку MediaStore, сохраняет
плейлист, избранное, историю и скрытие, затем удаляет исходную строку, изменяет теги
и создаёт файл по новому пути с новым ID. Новый экземпляр библиотеки восстанавливает
связи из сохранённого реестра. Проверены путь экспорта, top tracks/top artists и
чтение аудиосэмпла через Android MediaExtractor по новому URI. Ещё два теста
проверяют обновление MediaItem с сохранением ID, clipping и обложки, а также отсутствие
замены URI при обычном обновлении тегов. Использованы отдельные тестовые пакеты;
production-приложение и пользовательская медиатека не заменялись.

Тестовый MP3 — сгенерированный трёхсекундный синус, а не музыка пользователя.
Физический Android-телефон в этом прогоне не был подключён. Тест не воспроизводит
точную коллекцию автора issue и не заменяет проверку перемещения во время реального
воспроизведения на его устройстве.

Команда финального прогона (JDK 21, настроенный Android SDK):

```sh
./gradlew :core:library:testAndroidHostTest :composeApp:testAndroidHostTest \
  :core:history:testAndroidHostTest :core:playback:testAndroidHostTest \
  :core:smart:testAndroidHostTest :core:library:connectedAndroidDeviceTest \
  :core:playback:connectedAndroidDeviceTest :core:library:iosSimulatorArm64Test \
  :composeApp:iosSimulatorArm64Test --continue --console=plain
```

## Релизные артефакты

`build/reports/issue17-compact-release/provenance.json`: статус `verified`, чистый
`d7ae2800` до и после сборки. Сборка заняла 43 с. Выполнены DEX/native-гейты,
проверка ELF/ZIP 16 KiB и точных SHA-256 упакованных ORT-библиотек после stripping.
Это проверка сборки с прежним model-matched ORT 1.26.0, а не новый inference-parity
эксперимент. Использован Python из прежней проверенной сборки; системный Python 3.9
не поддерживает `hashlib.file_digest` и был заменён до запуска Gradle.

## Оставшиеся ограничения

Этот вариант предотвращает будущую потерю связей в подтверждённом однозначном
сценарии. После установки нужно дать приложению увидеть исходные файлы и завершить
фоновое чтение до переименования. Если файлы уже перемещены, старых идентификаторов
нет, тег изменился вместе с переносом или кандидаты неоднозначны, автоматического
восстановления не будет. Неверно проставленный одинаковый release-track ID сам
по себе не является доказательством побайтовой идентичности аудио.

Рекомендация: включить это ограниченное исправление в кандидат 0.9.1 и проверить
его на копии библиотеки автора issue перед заявлением о решении именно его случая.
Не закрывать issue как полностью решённый универсальным распознаванием.
